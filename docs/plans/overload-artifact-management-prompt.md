## 一、产品定位

Overload 的产品目标仍是解决人类注意力分配问题：减少无效打断，减少理解任务和重建现场的成本，让正确的人完成决策，并使任务可靠续跑、结果回流。

本次调整工程建模重心：
- 任务是长期容器。
- 输入、执行记录和版本化产物是任务的持久上下文。
- Session 是某个 Agent 的一次执行现场，不是任务上下文的唯一载体。
- Agent 可以替换，任务及其产物演进保持连续。
- 产物管理不是泛用文件盘，也不是另建一个日志监控平台。

核心闭环：外部 Agent 执行 → 自动发现 Session → 自动建立任务及输入、执行记录、产物关联 → 持续同步与版本留存 → 必要时提出人类决策 → 验收或跨 Agent 交接 → 新执行继续关联原任务 → 结果回流与归档。

## 二、已确认的产品要求

### 1. 自动发现与自动纳管

不要求任务由 Overload 启动。必须面向用户已经在外部启动的 Session。

默认自动发现可接入、可访问的外部 Session，自动建立任务和产物关联，不要求用户逐个确认纳管。

用户可以指定：
- Agent：全部已接入的 Agent，或选定 Agent。
- 时间范围：历史发现与回溯的范围。
- 是否持续发现之后出现的新 Session。

时间范围建议按“范围内有活动”筛选，而不只按 Session 创建时间。命中 Session 后，应在权限与可用数据范围内读取必要历史，避免截断目标和前置上下文。

区分发现范围、已纳管任务的持续同步、UI 查询筛选。改变发现范围或 UI 筛选，不应隐式删除已纳管任务和产物。已纳管任务默认继续追踪至结束，除非用户明确停止跟踪。方案须明确以上推荐语义及其代价。

“任意 Session”意味着开放的接入目标，不意味着无需适配、权限即可读取所有产品，也不承诺任意 Agent 内部状态可以无损迁移。

### 2. 输入管理

保存并关联用户原始需求、附件与引用材料、后续补充、约束变更、用户审批、验收和反馈。

保留版本、来源和时间信息。每次执行应能明确其依据的输入版本。用户消息、决策、工具调用、产物不能全部粗暴建模成同一种文件。

### 3. 执行过程管理

保存可取得的 Agent 与 Session 身份、对话记录、工具调用参数/结果/错误、文件读取和修改等可观察行为、已发生的外部动作、中间产物、验证证据、当前执行状态和未解决问题。

原始记录与整理后的摘要分开。摘要属于派生信息，必须可追溯，不替代原始证据。不得依赖或采集模型不可见的内部推理。不得声称能够补回从未记录或已经丢失的历史。

### 4. 产物管理

产物包括代码及代码变更、文档与报告、中间结果和最终文件、PR 等外部资源。

需支持稳定身份、版本、来源、与任务/Session/执行记录/输入版本的关联、验证和审核证据、外部目标的引用和提交结果。

不能只保存可变路径或 URL。本地文件应有必要快照及内容摘要。代码应考虑 commit、未提交修改、必要的未跟踪文件。外部资源保留稳定标识、URL 及可取得的版本信息。历史版本不可取得时明确标注，不能用当前内容冒充历史。

区分草稿/待验收/已接受与是否已提交或发布到外部目标。验收通过不等于提交成功，提交成功不等于已经合并或发布。审核必须绑定具体产物版本；产物改变后不能沿用旧版本的有效验收结论。

### 5. 自动关联规则

Session → 任务：
- 明确任务标识、父子 Session、续跑关系等强证据，可自动归入同一任务。
- 无明确关系时，自动建立独立任务。
- 同仓库、时间接近、文本相似只作为线索，不据此强制合并。

Session → 输入/执行记录/产物：
- 明确区分读取、引用、创建、修改、验证、提交等关系。
- “读过”不等于“产出过”；“目录中存在”不等于“由该 Agent 创建”。
- 关联记录证据来源和观察时间。
- 无法证明归属的内容标为现场材料或不确定关联。
- 多 Session 并发修改同一文件时，不能伪造唯一生产者。
- 不确定关联不应持续制造需要用户处理的噪声。
- 应考虑错误关联的纠正方式及已有证据的保留。

### 6. 跨 Agent 交接

目标是任务级接续，不是任意 Agent 内部状态的无损恢复。

用户选择另一个 Agent 后，系统建立可验证的交接点，至少包含当前目标与约束、当前输入版本、当前产物版本、已完成事项、已验证事项与证据、未完成事项和阻塞项、建议下一步、已发生的外部动作、仓库/分支/未提交修改/必要文件及环境要求、已知上下文缺口。

新 Agent 建立新的 Session，继续关联原任务，后续产物形成新版本，结果回流原任务。

同 Agent 的原 checkpoint 恢复与跨 Agent 的新执行必须明确区分。仅纳入管理，不代表获得原 Agent 控制权。

默认续跑保证只面向原执行已终止的场景。原 Agent 仍运行或 blocked-on-ask 时，优先返回原现场。不得静默启动另一个 Agent 对同一工作目录重复写入。主动停止原执行需要明确用户授权和实际停止确认。防止重复创建 PR、重复发布等副作用。

### 7. 能力分级与安全边界

为各接入源明确实际能力：
- 完整接入：可读取必要历史、工具记录和产物。
- 部分接入：存在明确的上下文缺口。
- 手动导入：作为无自动读取接口时的降级路径，不替代自动纳管主路径。

覆盖权限不足、数据源不可用、确实为空、历史被清理、Session 身份变化、文件被覆盖或删除、Agent 不可控制。

不可用不应当成空数据，更不能据此删除任务或产物。

凭证、token、敏感工具参数不得原样扩散到日志、产物库或交接包。不得无差别归档整个工作目录、依赖目录和无关文件。给出内容采集范围、大小限制、保留、清理及访问边界。

### 8. UI 与注意力原则

沿用 Now / Inbox / Done，不要求用户理解内部 Q1–Q5。

任务默认突出输入及已确认约束、当前产物及版本变化、验证结果、待决策问题、Agent 接力记录、能否交接及缺失什么、返回原现场的入口。

完整执行过程按需展开。普通发现、同步和进度不得主动打断用户。仅对风险、必要决策、不可恢复失败和最终验收占用注意力。同任务事件聚合、去重、原地更新，结果主动回流。

13. 测试和验收：单元、集成、端到端和故障注入；可重复的 fixture；可执行的验证命令或测试入口；明确通过与失败标准，不依赖人工盯 UI。

## 六、必须覆盖的验收场景

- 外部启动 Session，无需逐个确认即可自动纳管。
- 指定 Agent 与时间范围，正确回填且不漏掉范围内活跃的旧 Session。
- 重复扫描、进程重启不重复建任务或产物版本。
- 改变发现范围不删除已纳管数据。
- 普通进度不新增人类决策卡。
- 读取文件不被误记为生产文件。
- 同仓库不同任务不会仅因时间接近而被合并。
- 两个 Session 并发修改同一文件，不伪造来源或交接一致性。
- 产物覆盖或删除后，已保存版本仍能追溯。
- 数据源暂时不可用，不被解释为 Session 或产物消失。
- 只有部分历史时，仍能纳管，但明确交接缺口。
- 已终止的 Agent A 任务交给 Agent B，沿用同一任务、正确产物版本和已发生动作记录。
- 原 Session blocked-on-ask 时，不静默重启或并发写入。
- 交接启动失败可以恢复，不重复外部副作用。
- 验收绑定的产物改变后，旧验收不能用于新版本提交。
- 已接受产物但提交失败，不能显示为提交成功。
- 新 Agent 完成后，结果回到原任务，符合条件时自动归档。
- 敏感信息不进入可分享的产物或交接包。

## 七、工程约束

- YAGNI，优先复用现有代码和已安装依赖。
- 不默认引入新服务、新数据库、对象存储、向量库或消息队列。
- 若建议新增依赖或基础设施，必须证明当前能力不能覆盖。
- 确定性来源关联优先于模型猜测。
- 不对每条普通事件调用模型；说明摘要触发时机与成本预算。
- 不承诺恢复不可访问、未记录或已经丢失的信息。
- 不硬编码未经实际配置来源确认的路径、端口和凭证来源。
- 不用事件采集量或支持 Agent 数替代产品效果指标。

指标优先考虑：无效打断数、任务重建成本、返回现场耗时、跨 Agent 交接成功率、产物版本可追溯率、重复副作用数、通知压缩率、已结束事项清退率。
